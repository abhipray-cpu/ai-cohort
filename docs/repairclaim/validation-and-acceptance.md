# Validation and first-release acceptance

All gates remain **open**. G1 has unit/store, real PostgreSQL, native sandbox,
actual socket API/worker and packet-control evidence, plus frontend tests/build;
the full G1 gate and G0/G2–G5 are not passed. Target thresholds below are proposals to freeze
before evaluation, not measured results. Engineering completion, public-source
quality, consumer acceptance, host qualification and commercial demand are separate.
All FR-01–FR-12 must have proof; do not call an implementation-only result full MVP.

Latest [public repair-document checkpoint](public-repair-document-validation-2026-10-24.md)
adds seven real mixed attachment packs and expanded correction/confirmation,
historical-response/follow-up, reminder/export, approval and deletion checks.
It does not pass independent quality thresholds, browser accessibility, Windows
qualification or consented customer outcomes. Browser discovery is still empty
after supported troubleshooting; the browser connection has been requested.

## G0: scope, source and authority readiness

Reviewed supported inventory, legitimate acquisition/access, specialist condition
interpretation, private-data policy, finite campaign allowances, provider/source
capabilities and intended consumer exclusions. Unavailable account/data/host is an
explicit gap, not permission to use another customer's service or fabricate proof.

## G1: engineering and contract gates

Unit/property and real store/API integration tests cover all AT IDs, condition
boundaries, dedup/idempotency/revision fencing, source errors, PDF/image parsing,
amount/currency/outcome aggregation, scope/consent, approval and deletion. Retain
meaningful red→green records for each slice. Run repository regression and frontend
typecheck/test/build. No unexplained skip, expected-failure, flaky rerun or fake
adapter can count as proof of a real integration. Shared-package regressions block.

Security: complete two-household endpoint/file/job/inbox/export matrices; zero
unresolved critical/high access, disclosure, unsupported finalized-claim or financial
fabrication findings. Parser restrictions, redaction and erasure need actual-byte/
process tests, not snapshots alone. Outcome calculations must match an independent
Decimal oracle exactly for the tested cases.

## G2: frozen public-source quality and actual-provider E2E

Acquire, label and split the [planned corpus](data-and-evaluation.md); report any
volume/coverage shortfall explicitly. Freeze these initial targets before holdout:

- Candidate recall at least 95% and potential-lead precision at least 90% on labelled
  eligible/related cases; report per-family results and intervals, not just averages.
- At least 95% correct material condition extraction on reviewed public documents;
  zero missed mandatory exclusion that produces an unqualified supported claim.
- All observed quoted citations resolve to the bound source/version; at least 95%
  independently judged contextual support for material assessment claims.
- Zero unsupported material assertions in finalized evaluated packets. Any detected
  invented diagnosis/payment/eligibility claim blocks release until corrected and
  rerun on a fresh relevant holdout. Zero observed is not proof of zero population risk.
- All designated unknown/conflict/scope/outage cases remain appropriately qualified;
  no source failure masquerades as no coverage, and no bulletin-only case is presented
  as guaranteed free repair.
- At least 90% end-to-end completion to a correct useful terminal state under the
  frozen budget, counting failures/timeouts in the original denominator. Correct
  abstention can pass; unsupported certainty cannot. Report ready, abstained, failed
  and partial separately.

Live campaign verifies actual parser/retrieval/provider/draft/render/review flow.
Public source + authored invoice is labelled mixed-real/synthetic, not actual-consumer
E2E. Any threshold change after results requires a documented decision/new freeze;
do not tune away failures or average critical errors into a passing score.

## G3: real browser and consumer UI gates

Exercise actual running app, not only component mocks, at 360/768/1440 px:

| Scenario | Required observation |
| --- | --- |
| Paid repair with missing mileage | Original upload/fact correction → focused question → resume → sourced conditions |
| Wrong component / no supported lead | Clear qualified negative; no refund promise |
| Conflicting vehicle facts | Blocked finalization and useful correction flow |
| Packet | Actual rendered pages/attachments/redactions → exact approval → download; edit invalidates |
| Rejection | Response → attributed reasons → appropriate new evidence request/follow-up |
| Retrospective lead | Opt-in → reviewed source revision → deduplicated alert → old/new explanation |
| Approval stale after source change | Finalized download denied until re-review |
| Human control | No network message sent; manual send labelled user-reported |
| Outcome | Partial approval/payment/reversal distinguished without double counting |
| Family/privacy | Case-scoped helper, revoke, separate vehicle, export/delete and inaccessible links |
| Faults | Source/provider outage, partial preservation, session expiry, cancellation/restart |

Include keyboard/screen-reader critical paths and automated accessibility checks;
no serious/critical unresolved issues. Archive build ID, viewport, steps and safe
screenshots. Backend HTTP tests alone do not establish browser acceptance.

## G4: monitoring, durability, security and Windows deployment

Actual scheduler/outbox/crash tests show material versus cosmetic change, stale
invalidation, expiry/revocation/deletion races and no duplicate lead after restart.
At least one genuine programme revision pair is required for source-change quality;
injected changes remain fault tests. Review intentionally uncertain changes.

Qualify target Windows host/service/protected hostname using runbooks, resource
targets, origin isolation, sleep/wake, clock jumps, log privacy, credential separation,
backup/restore and tombstone reconciliation. Run one-hour soak at proposed capacity.
An unavailable laptop leaves deployment unaccepted; a macOS pass is not a Windows
pass. No universal uptime or commercial availability claim from this gate.

## G5: consented consumer/domain acceptance

Ten actual cases and five actual reply journeys as targeted in data/evaluation;
specialist review of all evaluated packets, documented user understanding, next-step
completion and consent/withdrawal. Apply UI comprehension targets and record real
effort. If no real cases exist, label the result an engineering/public-source pilot,
not full consumer acceptance. Reimbursement outcomes are reported only if observed.

Commercial validation is a separate ledger: interviews, alternatives, price testing,
pilot willingness and actual purchase evidence. A functioning MVP does not prove
that people will pay. Billing is not silently added to meet a business hypothesis.

## Evidence report and stop rules

Every run records commit/build, source/label/policy/provider versions, split, planned
versus attempted counts, bounds, authority, all attempts/failures/exclusions, metrics,
independent reviewer, artifacts and unresolved gates. Use fresh run IDs; never reuse
cached results after changing inputs. Stop on secret leakage, unauthorized data
egress, cross-household exposure, corrupt store, exceeded budget or safety-critical
unsupported advice. Preserve safe evidence, quarantine work and explain the issue.
Any failure remains in history after a later successful corrective run.
