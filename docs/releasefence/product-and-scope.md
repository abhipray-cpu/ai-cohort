# Product, customer and bounded scope

## Job to be done

An agent team changes prompt, model configuration and tool schema together.
Production task completion declines while latency and repeated tool calls rise.
The team needs to know which release/cohort is affected, whether to stop expansion,
and whether the previous compatible release is actually serving new sessions.

ReleaseFence proposes a cross-tool release-assurance workflow: register immutable
releases, connect permitted telemetry, define a policy, observe a limited canary,
alert on failure and verify an authorized rollback. The moat hypothesis is reliable
integration, operational evidence and customer-specific policy—not generic charts.

## Buyer and qualification

Target engineering/platform leads operating multiple customer-facing agents with
regular configuration releases and an existing tracing stack. Start with support
answer/draft workflows and a named release owner. Ask about the last real incident,
current investigation effort, false-alert tolerance and authority boundaries.

Not initial customers: hobby projects without production traffic; teams content
with their existing integrated platform; buyers demanding every cloud/controller
on day one; high-risk autonomous money movement or regulated decisions.

## First supported scope

- Multi-tenant organizations, projects, environments, applications and scoped actors.
- Python HTTP agent runtime adapter with immutable versioned bundle resolution;
  compatible workload can run in Docker or as a service. No arbitrary SSH executor.
- Customer-side OpenTelemetry collector; explicit `mlflow-phoenix-v1` profile
  with actual authenticated MLflow and customer-owned Phoenix connectivity.
  Legacy `langsmith-phoenix-v1` remains supported but LangSmith is unqualified;
  see [ADR 0002](adr-0002-self-hosted-mlflow.md). AX needs separate qualification.
- Metadata-first release/outcome/loop events and scoped trace deep links.
- Release dashboards, incident timeline, signed webhook notification delivery.
- Registered baseline/candidate, staged session-sticky routing, policy evidence
  and manual or explicitly preauthorized automatic rollback.
- Read-back verification, fresh-session probes and an unresolved-runtime list.
- GitHub Actions registration via scoped API token; no repository-wide admin grant.

Observe-only onboarding is useful without deployment authority. Controlled-release
mode requires an enrolled adapter and explicit application/environment capability.
UI must show the difference. A generic OTLP exporter alone is not full integration.

## Exclusions

No trace-backend replacement, hosted resale of third-party products, unrestricted
remote commands, arbitrary model edits, autonomous remediation generated by an LLM,
provider-billing reconciliation, guaranteed diagnosis, universal rollback, or
automatic reversal of emails/payments/database mutations. No launch claim of high
availability, compliance certification or all-cloud support.

The first product can prove routing/configuration rollback only within the enrolled
adapter. Compatible data/index snapshots must already exist; database migration
rollback and unavailable old model versions are not silently solved by a pointer.

## Product outcomes

Measure installation effort, time to identify an affected release, alert precision,
time to verified safe routing, unresolved in-flight exposure and operator effort.
Customer business outcomes need authorized pilot evidence and independent review.
No savings, accuracy or willingness-to-pay percentage is established yet.
